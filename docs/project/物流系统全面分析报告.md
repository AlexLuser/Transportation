## 二、物流系统建设所需核心算法

### 2.1 路径规划算法

#### A* 最短路径算法

| 属性 | 说明 |
|------|------|
| **实现类** | `AStarRouteStrategy` |
| **核心公式** | \(f(n) = g(n) + \epsilon \cdot h(n)\) |
| **g(n)** | 从起点到节点 n 的实际代价（路网累计距离） |
| **h(n)** | Haversine 球面距离启发值（保证可采纳性） |
| **ε (epsilon)** | 激进系数：1.0=标准A*（保证最优），1.8=中等激进，3.5=高度激进 |
| **数据结构** | PriorityQueue（最小堆）+ HashMap(gScore/cameFrom) |
| **路网引擎** | GraphHopper 9.x + 上海 OSM 数据 (`shanghai-260310.osm.pbf`) |
| **时间复杂度** | \(O(E \log V)\)，E=边数，V=节点数 |

```java
// 核心搜索伪代码
PriorityQueue<int[]> openSet = new PriorityQueue<>(Comparator.comparingDouble(a -> a[1]));
// a[0] = 节点ID, a[1] = f值（double转long存储）
openSet.add(new int[]{startNode, 0});

while (!openSet.isEmpty()) {
    int current = openSet.poll()[0];  // 取出f值最小的节点
    if (current == endNode) return reconstructPath(cameFrom, current);

    EdgeIterator iter = explorer.setBaseNode(current);
    while (iter.next()) {
        int neighbor = iter.getAdjNode();
        double tentativeG = gScore.get(current) + iter.getDistance();
        if (tentativeG < gScore.getOrDefault(neighbor, Double.MAX_VALUE)) {
            cameFrom.put(neighbor, current);
            gScore.put(neighbor, tentativeG);
            double h = haversine(nodeAccess.getLat(neighbor), nodeAccess.getLon(neighbor),
                                 nodeAccess.getLat(endNode), nodeAccess.getLon(endNode));
            double f = tentativeG + epsilon * h;
            openSet.add(new int[]{neighbor, (int)(f)});
        }
    }
}
```

#### LLM_JUDGE 裁判策略

| 属性 | 说明 |
|------|------|
| **实现类** | `LlmJudgeRouteStrategy` |
| **流程** | 生成3条不同ε的A*候选 → 查询历史交通数据 → DeepSeek选最优 |
| **候选生成** | ε ∈ {1.0, 1.8, 3.5} 产生差异化路线 |
| **去重机制** | 距离差 < 1% 视为相同路线，自动去重 |
| **历史上下文** | 当前小时均速/全天均速/speedRatio/延误/慢速热点/异常次数 |
| **降级策略** | LLM 调用失败 → 直接返回 ε=1.0 的标准A*结果 |

```
① A*(ε=1.0) → 候选1: 距离8.3km, 预计12min
② A*(ε=1.8) → 候选2: 距离9.1km, 预计14min
③ A*(ε=3.5) → 候选3: 距离11.2km, 预计15min
   + 历史交通数据（speedRatio=0.56严重拥堵, 慢速热点坐标...）
   ↓
④ 发送给 DeepSeek API (temperature=0.1, 强制JSON输出)
   ↓
⑤ 解析 LlmDecisionResult: {selectedCandidate: 2, reasoning: "绕开慢速热点", confidenceLevel: "HIGH"}
   ↓
⑥ 返回候选2作为最终路线
```

#### LLM_WAYPOINT 路点辅助策略

| 属性 | 说明 |
|------|------|
| **实现类** | `LlmWaypointRouteStrategy` |
| **流程** | 查历史数据 → LLM分析拥堵 → 建议绕行路点(0~2个) → 分段A*执行 → 合并GeoJSON |
| **防幻觉** | 检查LLM坐标是否在上海区域框 `[30.6~31.9, 120.8~122.2]` 内 |
| **兜底映射** | `locationIndex.findClosest()` 将任意坐标映射到最近真实路网节点 |

#### VRP 车辆路径规划

| 属性 | 说明 |
|------|------|
| **实现类** | `NearestNeighborVrpStrategy` |
| **用途** | Hub-and-Spoke 模式中末端多停靠点的访问顺序优化 |
| **算法** | 最近邻启发式（贪心），每次选择距当前位置最近的未访问点 |
| **时间复杂度** | \(O(n^2)\)，n=停靠点数量 |

### 2.2 图论与网络流算法

#### 最小费用最大流 (MCMF)

| 属性 | 说明 |
|------|------|
| **实现类** | `McmfServiceImpl` |
| **用途** | 全国干线流量分配——在保证流量最大的前提下使总费用最小 |
| **算法** | SPFA 找最短路增广 + 连续增广直到无可行增广路 |
| **应用场景** | 多仓库到多Hub间的批量运力分配优化 |

#### K-Means 地理聚类

| 属性 | 说明 |
|------|------|
| **实现类** | `KMeansClusterServiceImpl` |
| **距离度量** | Haversine 球面距离（非欧氏距离） |
| **用途** | 将地理邻近的订单归入同一配送批次（Hub-and-Spoke 模式） |
| **输入** | 一组订单的目的地坐标 (lat, lng) |
| **输出** | K 个聚类簇，每簇分配一个 Hub 进行统一配送 |

### 2.3 数据分析与聚合算法

#### 时空网格聚合（慢速热点识别）

```sql
-- LogisticsTrackMapper.selectSlowZones() 核心 SQL
SELECT ROUND(latitude, 2) AS latBucket,       -- 约1km网格聚合
       ROUND(longitude, 2) AS lonBucket,
       AVG(speed) AS avgSpeed,
       COUNT(*) AS occurrences,
       HOUR(MAX(track_time)) AS peakHour
FROM logistics_track
WHERE speed IS NOT NULL AND speed > 0
  AND track_time >= DATE_SUB(NOW(), INTERVAL 7 DAY)  -- 近7天
  AND latitude  BETWEEN #{minLat} AND #{maxLat}       -- 以起终点为中心的区域
  AND longitude BETWEEN #{minLon} AND #{maxLon}
GROUP BY ROUND(latitude, 2), ROUND(longitude, 2)
HAVING AVG(speed) < 8 AND COUNT(*) >= 3             -- 低速阈值 + 最小出现次数过滤噪声
ORDER BY AVG(speed) ASC
LIMIT 5
```

#### 按小时速度统计

| 属性 | 说明 |
|------|------|
| **方法** | `selectAvgSpeedByHour()` |
| **数据源** | 过去30天 `logistics_track.speed` / `track_time` |
| **输出** | 各小时的 `avgSpeed`、`sampleCount` → 计算 `speedRatio`(当前小时均速/全天均值) |
| **用途** | 为 LLM 提供当前时段交通状况的量化指标 |

#### 异常检测统计

| 属性 | 说明 |
|------|------|
| **方法** | `selectExceptionStats(startLat, startLon)` |
| **范围** | 起点附近约 2km、近 7 天内 |
| **条件** | `route_status = 3`（异常）的路线计数 |
| **输出** | 近期异常发生频次，供 LLM 判断路线风险 |

### 2.4 AI 决策算法

| 功能模块 | 实现类 | 输入 | 输出 | 用途 |
|---------|--------|------|------|------|
| Hub 中转站选择 | `LlmHubSelectionServiceImpl` | 距离 + 负载 + 交通数据 | 最佳Hub ID | 自动选择最优中转站 |
| 干线费用校准 | `LlmEdgeCostCalibrationServiceImpl` | 边的历史通行数据 | 费用倍率调整 | MCMF边的动态费用修正 |
| 全局调度建议 | `GlobalDispatchAdviceServiceImpl` | 全部待调度订单池 | 批次划分方案 + 是否中转建议 | 调度员决策辅助 |
| 订单紧急性检测 | `checkUrgency()` | 订单特征（商品/时效要求等） | 急送优先级标记 | 高优先级订单插队处理 |

所有 AI 决策共用 `DeepSeekClient`：
- API：`POST https://api.deepseek.com/v1/chat/completions`
- 参数：`temperature=0.1`（低随机性）、`response_format=json_object`（强制JSON）
- 容错：调用失败自动降级为规则-based 的默认策略

### 2.5 系统架构级技术设计

#### 策略模式（Strategy Pattern）

```
RouteStrategy (接口)
    ├── plan(startLat, startLng, endLat, endLng) → RouteResultDTO
    ├── planMultiStop(coords[]) → RouteResultDTO[]
    └── strategyName() → String
            │
    ┌--------┼────────┐
    ▼        ▼        ▼
AStarRoute   LlmJudge   LlmWaypoint
Strategy     Route      Route
    Strategy   Strategy
    (@Service)  (@Component)

RoutingStrategyConfig:
  @Bean @Primary RouteStrategy routeStrategy()
    switch(routing.strategy):
      "A_STAR"       → aStarStrategy
      "LLM_JUDGE"    → llmJudgeStrategy
      "LLM_WAYPOINT" → llmWaypointStrategy
```

运行时切换只需修改 `application.yml`：
```yaml
routing:
  strategy: A_STAR    # 可选: A_STAR / LLM_JUDGE / LLM_WAYPOINT
```

#### 最终一致性（Eventual Consistency）

```java
// order-service 发货逻辑（关键设计）
try {
    driverFeignClient.createDelivery(...);    // 可能失败
} catch (Exception e) {
    log.error("创建配送记录失败，待人工补偿: {}", e.getMessage());
    // 不抛异常！不回滚订单！
}

try {
    logisticsFeignClient.createRoute(...);    // 可能失败
} catch (Exception e) {
    log.error("创建物流路线失败，待人工补偿: {}", e.getMessage());
    // 不抛异常！
}
// 订单状态已更新为"待揽件"，单个下游服务故障不影响主流程
```

#### 原子操作防超卖

```sql
-- 单条SQL完成"检查+扣减"，数据库行锁保证原子性
UPDATE warehouse_product
SET stock = stock - #{quantity}
WHERE warehouse_id = #{warehouseId}
  AND product_id = #{productId}
  AND stock >= #{quantity}   -- 库存不足时影响行数=0，Java层判断affected==0则报"库存不足"
```

#### JWT 无状态认证

```
请求流程:
前端 Axios → 携带 Authorization: Bearer <JWT>
         → 网关 JwtAuthFilter
           ① 验证签名 + 有效期
           ② 解析 userId / username / roleCode
           ③ 权限矩阵检查（角色能否访问该API路径）
           ④ 注入请求头: userId, username, roleCode（小写头名）
           ⑤ 转发到目标微服务
         → 下游服务通过 @RequestHeader("userId") 读取用户身份（无需查数据库）
```

### 4.6 核心代码解析：原子扣减库存

```java
// ====== Mapper 层：原子 SQL ======
@Mapper
public interface WarehouseProductMapper extends BaseMapper<WarehouseProduct> {

    // 自定义 UPDATE SQL：一条语句完成 检查+扣减
    @Update("UPDATE warehouse_product " +
            "SET stock = stock - #{quantity} " +
            "WHERE warehouse_id = #{warehouseId} " +
            "AND product_id = #{productId} " +
            "AND stock >= #{quantity}")          // ★ 关键条件：只有库存足够才扣减
    int deductStock(@Param("warehouseId") Long warehouseId,
                    @Param("productId") Long productId,
                    @Param("quantity") Integer quantity);
}

// ====== Service 层：判断结果 ======
@Service
public class StockServiceImpl implements StockService {

    public boolean deductStock(Long warehouseId, Long productId, Integer quantity) {
        int affected = warehouseProductMapper.deductStock(warehouseId, productId, quantity);
        return affected > 0;   // 影响行数>0=成功, =0=库存不足被拒绝
    }
}
```

**为什么能防超卖？**

```
时刻T1: 仓库A 商品X 库存=5
时刻T2: 用户甲线程 → UPDATE ... SET stock=stock-5 WHERE stock>=5 → 成功! affected=1, 库存=0
时刻T2: 用户乙线程 → UPDATE ... SET stock=stock-5 WHERE stock>=5 → 失败! affected=0 (当前stock=0,不满足>=5)
                                                     → Java层: affected==0 → 抛 BusinessException("库存不足")
```

MySQL InnoDB 的行锁保证了即使两个请求**同时到达**，也会串行执行这条 UPDATE，不可能出现两个事务同时读到 stock=5 的情况。
