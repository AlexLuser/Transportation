# 提示词模式与经验教训记录 (Prompt Patterns & Lessons Learned)

## 1. 参考图驱动的架构图重绘模式 (Reference-driven Diagram Redraw Pattern)
**适用场景**：当用户明确给出一张"像这样"的参考图，并要求系统架构图、前端架构图等论文插图在视觉上靠拢该参考图时。

**Prompt 通用模式**：
> "请先定位论文中这几张图的源文件与引用方式，再按照我给的参考图重画。系统架构图请采用'左侧层级标签 + 右侧技术矩阵块'的规整布局；如果 Typst 原生布局难以稳定复现，就直接用脚本生成白底高清 PNG，并回写论文引用。与此同时，把另外两张相关图的边框、留白、字号和弱配色统一掉。"

**经验教训 (Lessons Learned)**：
- 用户已经给了参考图时，**第一优先级是对齐视觉语法**（分层、留白、盒子排列、灰度风格），而不是先陷进某个绘图库的局部参数调优。
- 对毕业论文中的**规整分层架构图**，脚本生成静态 PNG 往往比在 Typst/Facade 中硬调复杂布局更稳定，尤其当目标风格接近 draw.io/Visio 这类成品图时。
- `Mermaid` 适合流程图和简化 ER 图，但不适合复刻这种"矩阵式、表格化、低饱和"的系统架构图。
- 重绘时应同时检查：**宽高比是否适配 A4 页宽、底色是否纯白、边框与字号是否统一、是否存在空白过多或元素互相遮挡**。

## 2. 工具选择与调研模式
**适用场景**：当用户提供多个待选方案（echarts、graphviz、typst包等）时。

**Prompt 通用模式**：
> "请先搜索网络或包管理器中的相关生态（如搜索 npm、typst universe 等），对比各工具的特点（如：echarts 适合数据图表、graphviz 适合关系拓扑、facade 适合嵌套分层架构图），根据输入中要求的'特点（比如有分层颜色背景）'，为我推荐最适合并给出直接可运行的代码。"

**经验教训**：
- 仔细阅读需求中指出的"缺陷"（如之前的评价中指出无分层背景、无泳道等），针对性地去查找能弥补这些缺陷的图表工具包。对于带颜色背景和层级包含关系的，直接锁定原生排版的 Flex 布局插件或 PlantUML/draw.io。

## 3. Typst Mermaid 多图渲染 Bug 与规避模式
**适用场景**：当需要在同一个 Typst 文档中使用 `@preview/mmdr`（Mermaid引擎）渲染多张图表（如切分多个 E-R 子图），尤其是放在 `#grid` 等复杂排版结构中时。

**Prompt 通用模式**：
> "由于 `@preview/mmdr` 在 Typst 单文件多次调用时存在文字重叠、画布截断等严重的渲染 Bug，请不要将所有 `#mermaid()` 调用写在同一个主文件中。请将每个 Mermaid 子图独立保存为一个 `.typ` 文件（设置 `#set page(width: auto, height: auto, margin: 5pt)`），独立编译为 `.png` 或 `.svg`，然后在主文件中通过 `#grid(image(), ...)` 进行组合。"

**经验教训 (Lessons Learned)**：
- 避免试图通过调整 Mermaid 代码（如改变实体定义顺序）来强行拯救过于拥挤的 E-R 单图，按照**领域驱动设计（DDD）**将复杂的大图按业务域拆分为多个子图是排版和学术展示的最佳实践。
- 坚决不要在 Typst 主文档的 `#grid` 布局中混用多个 `#mermaid()` 宏块，这会导致无法预测的底层布局碰撞（如生成出来的 PNG 图像损坏或内容重叠错乱）。物理拆分并独立编译图片是最可靠的工程方案。

## 4. 论文型核心 E-R 图收敛模式
**适用场景**：当用户明确要求把 E-R 图做得更像学位论文插图，而不是数据库全表总览或系统后台结构图时。

**Prompt 通用模式**：
> "请不要把所有表和关系都塞进一张 E-R 图。先从数据库中抽取支撑论文论述的核心实体，按业务域分组排版，只保留关键外键和主要基数关系；复杂的中间表、日志表和字段细节下放到关系表说明。整体风格采用低饱和分组框、统一实体卡片和细线连接，输出适合 A4 论文页宽阅读的高清静态 PNG。"

**经验教训 (Lessons Learned)**：
- **论文型 E-R 图优先服务于解释性，而不是穷举性**；把所有表塞满通常会得到"可导出但不可读"的图。
- 当一张图需要同时承担"概念说明"和"字段查阅"两种职责时，应让图只保留核心实体与基数，把精确字段明细交给后续关系表。
- 对于毕业论文页宽，实体数量一多就应主动做抽象收敛；相比继续堆实体，减少一层细节往往比调字号更有效。

## 5. 论文图片"已生成但未刷进PDF"排查模式
**适用场景**：当用户怀疑新重绘的论文插图没有真正进入最终 `PDF`，尤其是在 `Typst` 中同一位置可能同时存在旧的原生绘图代码和新的 `PNG` 方案时。

**本轮原始 Prompt 记录**：
> "架构总览图没有刷上去，你看看你刚才画的图真的刷到 /Users/miao/CodeBuddy/thesis-transportation/thesis-output.pdf 里了吗"

**Prompt 通用模式**：
> "请不要只看图片文件的修改时间。先检查论文主文件里该图究竟是 `image(...)` 引用还是旧的 Typst/Facade 绘图代码；然后重新编译 PDF，并用 PyMuPDF 定位包含该图标题的页面，检查该页是否存在图片对象，必要时把 PDF 内嵌图片提取出来，与源 PNG 做尺寸或像素级比对，最后再确认页码和落版结果。"

**经验教训 (Lessons Learned)**：
- **PNG 文件更新 ≠ 论文已引用新图**；如果正文仍保留旧的 `#figure(...)`/`facade` 内容，重编后 PDF 仍会显示旧版本。
- 判断"有没有刷进去"时，不能只看 `pdf` 的修改时间，必须同时核对**主文档引用方式、目标页图片对象、提取后的内嵌图片内容**。
- 对 `Typst` 论文，`PyMuPDF` 的 `page.search_for()`、`page.get_images()` 和 `extract_image()` 是非常高效的最终验收链路。

## 6. 全局 E-R 总图可读性不足时的撤图模式
**适用场景**：当系统跨多个业务域，哪怕已经做过概念收敛，整张总 E-R 图在 A4 论文页宽下仍显拥挤、凌乱，不足以支撑正式排版时。

**本轮原始 Prompt 记录**：
> "这个ER图还是很丑陋，你自己读取那个png不觉得丑陋吗，思考一下你还有没有什么办法优化。我感觉如果优化不好，要不论文里就不放这个图了"

**Prompt 通用模式**：
> "请先诚实评估当前全局 E-R 图是否真的适合放进学位论文正文。如果已经去掉字段细节、改成概念图之后仍然不好看，就不要继续在单张总图上死磕；改为保留文字概述与核心实体关系汇总表，撤掉正文中的总 E-R 图引用，并说明撤图原因是版面美观和可读性优先。图文件可以保留为工作稿，但正文不要硬放。"

**经验教训 (Lessons Learned)**：
- **不是所有系统都适合在正文里放"一张全局 ER 总图"**；跨域关系一多，即使逻辑正确，也很容易牺牲观感。
- 当图的职责与后续关系表高度重合时，图的增益会下降；这时撤图、保留结构化文字和表格，往往比留下丑图更专业。
- 对学位论文来说，**宁可少一张不够美观的图，也不要为"形式完整"硬塞一张观感欠佳的总图**。

## 5. 项目目录清理与收敛模式 (2026-05-18)
**适用场景**：当项目经历了多次迭代，产生了评估阶段的原始模板副本、重复文档、过期引用等冗余内容时。

**Prompt 通用模式**：
> "帮我清理没用的内容，收口到最佳实践"

**经验教训 (Lessons Learned)**：
- **评估阶段的原始模板不应留在项目目录内**。`thesis-latex/` 和 `thesis-typst/` 是早期下载的学校模板原版，最终选型后内容已全部迁移到独立仓库 `thesis-transportation/`，原模板应删除（随时可从 GitHub 重新下载）。
- **论文独立仓库与代码项目不应合并为 monorepo**：git 历史独立性、仓库公开/私有没有定位、体积膨胀（论文仓库含 slides/node_modules 559MB）、技术栈无关（Typst vs Java/Docker）都是理由。保持 `thesis-transportation` 独立即可。
- **docs/ 下文件做了子目录分类后**，根目录下的旧文件应在 git 中 stage 删除（`git add -u`），否则 git status 会一直显示 `D`（deleted but unstaged）。
- **`.gitignore` 要同步更新**：删除目录后移除对应条目，新增路径的忽略规则要补齐（如 `docs/reference/` 下的 PDF、`docs/thesis/` 下的提取文本）。
- **资源备忘录中的路径引用要同步修正**：比如 `论文源码` 的路径从旧位置更新为 `/Users/miao/CodeBuddy/thesis-transportation/template/thesis.typ`。
