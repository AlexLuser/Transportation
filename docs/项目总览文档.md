## 1. 项目简介

### 1.1 这是什么系统？

**智能物流管理系统**是一个面向电商物流场景的**微服务架构**应用，支持四类用户角色协同工作：

| 角色 | 登录标识（roleCode） | 核心功能 |
|------|---------------------|----------|
| **管理员** | `admin` | 全局数据监控、用户管理、商品和订单总览 |
| **顾客** | `customer` | 商城浏览购物、下单、查看物流轨迹地图 |
| **商户** | `shop` | 管理商品/库存/仓库，处理订单发货 |
| **运输员** | `driver` | 接取配送任务、上报 GPS 位置、确认送达 |

### 1.2 系统的核心价值

1. **智能路线规划**：集成 GraphHopper（基于 OSM 真实路网）和 DeepSeek 大语言模型，支持三种路线规划策略（A*、LLM评判、LLM路点辅助），避开历史拥堵区域
2. **实时物流追踪**：运输员上报 GPS，顾客端地图实时显示规划路线（蓝色虚线）+ 实际轨迹（橙色实线）
3. **原子库存扣减**：数据库级 `UPDATE ... WHERE stock >= quantity` 防止超卖
4. **全链路角色隔离**：网关层 JWT 验证 + 路由级权限矩阵，保证各角色只能访问自己的资源

### 1.3 核心业务场景一句话描述

```
顾客下单 → 商户发货 → 系统自动规划路线 → 运输员接单配送 → GPS实时上报 → 顾客地图查看 → 确认送达
```

### 2.2 请求生命周期

```
用户操作（如点击"下单"）
    ↓
Vue 组件调用 API 函数 (api/order.ts)
    ↓
Axios 请求拦截器：自动注入 Authorization: Bearer <token>
    ↓
POST /api/orders  → Vite proxy 转发 → 网关 localhost:8083
    ↓
网关 JwtAuthFilter：
  ① 验证 JWT 签名与有效期
  ② 解析 userId / username / roleCode
  ③ 检查角色权限（customer 可访问 /api/orders/** ？YES）
  ④ 将用户信息注入请求头（userId, username, roleCode）
  ⑤ 负载均衡转发到 order-service 实例（lb://order-service）
    ↓
order-service 业务层：
  读取 @RequestHeader("userId")、@RequestHeader("roleCode") 获取调用者身份
  调用 customer-service / shop-service / driver-service / logistics-service
    ↓
各下游服务处理完毕，层层返回
    ↓
Axios 响应拦截器：统一检查 result.code，非200则弹错误提示
    ↓
Vue 组件更新 DOM，用户看到结果
```

| **common** | 无（库） | — | 共享DTO、JWT工具类、统一响应、异常处理 | — |
| **customer-service** | 8084 | customer DB | 顾客信息管理、收货地址 CRUD | 10个 |

| **order-service** | 8086 | order DB | 订单全生命周期管理（中枢服务） | 15个 |

| **logistics-service** | 8087 | 与各服务共用 `transportation` 库（表前缀隔离） | 路线规划（A*/LLM）、GPS追踪、历史分析 | 见 Swagger |
| **frontend** | 5173（开发） | — | 四角色 Web 端界面 | — |

### 3.2 服务详细说明

#### gateway-service — 系统大门
- **唯一的外部入口**，所有前端请求都经过此服务
- 使用 **Spring WebFlux（响应式框架）**，非阻塞，高并发处理能力
- **白名单**：`/api/auth/login`、`/api/auth/logout`、`/*/v3/api-docs`（Swagger）
- **权限矩阵**：
  ```
  /api/admin/**   → 仅 admin 访问
  /api/customers/**、/api/address/**、/api/mall/**  → customer 访问
  /api/shops/**、/api/products/**、/api/warehouses/**、/api/stocks/**  → shop 访问
  /api/drivers/**  → driver 访问
  /api/orders/**   → customer 和 shop 和 driver 和 admin 共同访问（不同操作）
  /api/logistics/** → customer 和 driver 和 admin 访问
  ```

#### auth-service — 认证服务
- 查询 `user` 表，使用 **BCrypt** 验证密码哈希
- 签发 **JWT Token**（2小时有效期，包含 userId/username/roleCode）
- JWT 密钥和有效期通过 `@Value` 从配置文件注入

#### customer-service — 顾客服务
- 管理 `customer_info` 表（顾客档案）和 `customer_address` 表（收货地址）
- **默认地址管理**：`@Transactional` 保证"取消旧默认→设置新默认"的原子性
- 提供内部 API（`/internal/user/{userId}`、`/address/{addressId}`）供 `order-service` 调用

#### shop-service — 商铺服务
- 管理商铺、商品（含多图片 JSON 存储）、仓库（含 GPS 坐标）、库存（多仓库多商品）
- **原子库存扣减**：`UPDATE warehouse_product SET stock = stock - #{qty} WHERE stock >= #{qty}`，用数据库行锁防止超卖
- 商城端（`MallController`）为顾客提供公开商品浏览（`status=1` 在架商品）

#### order-service — 订单服务（中枢）
- 全系统**调用其他服务最多**的模块，是业务流程的协调者
- **快照设计**：`order_item` 保存下单时的商品名称和价格，防止商品修改影响历史订单
- **状态机**：`0待支付→1待发货→2待揽件→3派送中→4已完成`，`5=已取消`
- **最终一致性**：发货时调用 `driver-service` 和 `logistics-service` 失败，只记录日志，不回滚订单（最终一致性设计）

#### driver-service — 运输员服务
- **幂等创建配送任务**：检查 `orderId` 是否已存在记录，避免重复创建
- **接单触发链**：接单 → 绑定司机车辆 → 调 `order-service` 更新订单状态（→派送中） → 调 `logistics-service` 绑定司机到路线
- **取消配送**：清空司机/车辆绑定 → 重置配送状态 → 调 `logistics-service` 标记异常 → 调 `order-service` 回退订单状态

#### logistics-service — 物流服务（AI智能路线）
- **三种路线策略**（可通过配置切换）：
  - `A_STAR`：纯 A* 算法，基于 GraphHopper 路网，最快
  - `LLM_JUDGE`：生成3条 A* 候选路线，由 DeepSeek LLM 根据历史拥堵数据选最优
  - `LLM_WAYPOINT`：LLM 建议中间路点（绕开拥堵区），分段 A* 规划
- **GPS 追踪**：存储 `logistics_track`（历史轨迹）并更新 `logistics_route.current_lat/lng`（实时位置）
- **抗幻觉机制**：LLM 生成的坐标如不在上海区域（约束框检查），自动映射到路网最近节点

## 5. 核心业务流程

### 5.1 完整订单生命周期

```
状态：0=待支付  1=待发货  2=待揽件  3=派送中  4=已完成  5=已取消

顾客操作：
  [商城浏览商品] → [加入购物车/立即购买] → [填写地址/确认订单]
        ↓
  [POST /api/orders]（顾客下单）
        ↓
  order-service 处理：
    ① 验证地址（→customer-service）
    ② 验证商品 + 扣库存（→shop-service，原子操作）
    ③ 创建 order_info（当前实现：**直接为待发货 status=1、已支付**，毕设简化）
    ④ 创建 order_item（快照商品名称/价格）
        ↓
  订单状态：1（待发货）
  （可选）若使用 [PUT /api/orders/{id}/pay]：再次校验归属并置已支付，与创建逻辑并存于不同入口
        ↓ 商户点击"发货"
  [PUT /api/orders/{id}/status]（body: orderStatus=2）
        ↓
  order-service 处理：
    ① 获取地址详情（→customer-service）
    ② 获取仓库坐标（→shop-service）
    ③ 创建配送记录（→driver-service，进入待接单大厅）
    ④ 规划物流路线（→logistics-service，A*/LLM）
        ↓
  订单状态：2（待揽件）
  配送状态：0（待接单）
  路线状态：0（待出发）
        ↓ 运输员在"待接单大厅"接单
  [POST /api/drivers/deliveries/{id}/accept]
        ↓
  driver-service 处理：
    ① 绑定 driverId + vehicleId 到配送记录
    ② 更新配送状态：0→1（已接单）
    ③ 更新订单状态：2→3（→order-service）
    ④ 绑定司机到物流路线（→logistics-service）
        ↓
  订单状态：3（派送中）
  配送状态：1（已接单）
  路线状态：0（待出发）
        ↓ 运输员点击"开始运输"
  [PUT /api/drivers/deliveries/{id}/status]（status→2）
        ↓
  driver-service：更新配送状态1→2，调 logistics-service 路线状态→1（运输中）
        ↓ 运输员定时上报 GPS（Navigation页面）
  [POST /api/logistics/track/location]
        ↓
  logistics-service：记录 logistics_track，更新 logistics_route.current_lat/lng
  （顾客刷新订单详情，RouteMap组件拉取新轨迹，实时显示当前位置）
        ↓ 运输员点击"确认送达"
  [PUT /api/drivers/deliveries/{id}/status]（status→3）
        ↓
  driver-service：更新配送状态2→3，调 logistics-service 路线状态→2（已送达），
                  调 order-service 订单状态3→4（已完成）
        ↓
  订单状态：4（已完成）✓
```

### 5.2 取消流程

```
订单在 0（待支付）或 1（待发货）时，顾客/商户可取消：
  [DELETE /api/orders/{id}/cancel]
        ↓
  order-service：更新 status→5，记录 cancel_reason（前端传入原因文字）

如果订单已到 2（待揽件），配送记录已创建，运输员可取消接单：
  [DELETE /api/drivers/deliveries/{id}]
        ↓
  driver-service：
    ① 清空 driverId/vehicleId，重置配送状态→0（回到待接单大厅）
    ② 调 logistics-service 路线状态→3（异常）
    ③ 调 order-service 重置订单→2（待揽件，等待其他运输员接单）
```

## 6. 数据库设计总览

### 6.1 数据库实例划分

当前本地配置（各服务 `application.yml`）普遍指向 **同一 MySQL 库名 `transportation`**，通过**不同表**划分业务边界；生产环境可再拆分为多库。核心表归属如下：

| 逻辑归属 | 核心表 |
|---------|--------|
| customer-service | `user`, `customer_info`, `customer_address` |
| shop-service | `shop_info`, `product_info`, `warehouse`, `warehouse_product` |
| order-service | `order_info`, `order_item` |
| driver-service | `driver_info`, `vehicle`, `order_delivery` |
| logistics-service | `logistics_route`, `logistics_track`, `logistics_node` |

> **服务间仍只通过 REST/Feign 访问数据**，不跨服务直连对方表，以便日后拆库。

### 6.2 核心表结构

#### user 表（在 customer_db）
```sql
CREATE TABLE user (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    username    VARCHAR(50) UNIQUE NOT NULL,
    password    VARCHAR(255) NOT NULL,  -- BCrypt 哈希，如 $2a$10$...
    permission  INT NOT NULL,           -- 1=管理员 2=顾客 3=商户 4=运输员
    create_time DATETIME,
    update_time DATETIME
);
```

#### order_info 表（核心：订单主表）
```sql
CREATE TABLE order_info (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no        VARCHAR(30) UNIQUE,  -- 格式：ORD+日期+4位随机数
    customer_id     BIGINT,              -- 关联 customer_info.id
    shop_id         BIGINT,              -- 关联 shop_info.id
    address_id      BIGINT,             -- 收货地址 ID（快照地址字段更好，但此处存ID）
    order_status    INT DEFAULT 0,       -- 0待支付 1待发货 2待揽件 3派送中 4完成 5取消
    payment_status  INT DEFAULT 0,       -- 0未支付 1已支付
    product_amount  DECIMAL(10,2),      -- 商品总价
    shipping_fee    DECIMAL(10,2),      -- 运费
    total_amount    DECIMAL(10,2),      -- 订单总金额
    cancel_reason   VARCHAR(255),        -- 取消原因
    remark          VARCHAR(500),        -- 买家留言
    customer_deleted TINYINT DEFAULT 0,  -- 软删除标志（顾客端"删除"只是隐藏）
    create_time     DATETIME,
    payment_time    DATETIME,
    shipping_time   DATETIME,
    complete_time   DATETIME
);
```

#### order_item 表（快照设计）
```sql
CREATE TABLE order_item (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id        BIGINT,             -- 关联 order_info.id
    product_id      BIGINT,             -- 商品 ID（仅记录，不关联）
    product_name    VARCHAR(255),       -- ★快照：下单时的商品名称
    product_price   DECIMAL(10,2),     -- ★快照：下单时的商品单价
    product_image   VARCHAR(500),      -- ★快照：下单时的商品图片
    quantity        INT,                -- 购买数量
    subtotal        DECIMAL(10,2)      -- 小计（price × quantity）
);
-- 为什么要快照？商品名称/价格可能变化，历史订单必须保留下单时的信息
```

#### logistics_route 表（路线主表）

列名与 `database/logistics.sql` 一致：经纬度列为 **`start_lat` / `start_lng`、`end_lat` / `end_lng`、`current_lat` / `current_lng`**（Java 实体为驼峰）；含 **`route_no`、`warehouse_id`、`delivery_id`、`last_track_time`、`estimated_arrival_time`、`actual_arrival_time`** 等；规划结果存 **`planned_route`（GeoJSON）**；**无**库内 `planned_distance` / `route_strategy` 字段。

#### logistics_track 表（GPS轨迹）

含 **`heading`（方向角）**、**`accuracy`、`altitude`、`track_time`（业务上报时间）**、`create_time`（服务端时间）等；列表/最近接口按 **`track_time` 倒序**，完整历史按 **`track_time` 正序**。详见 `database/logistics.sql`。

### 6.3 跨服务数据关联关系

```
user.id ──────────────────→ customer_info.user_id（登录账号→顾客档案）
customer_info.id ─────────→ order_info.customer_id（顾客→订单）
customer_address.id ──────→ order_info.address_id（地址→订单）
shop_info.id ─────────────→ order_info.shop_id（商铺→订单）
```

## 10. 系统特色技术亮点

### 10.1 三级路线规划策略

```
配置项：`routing.strategy=A_STAR` / `LLM_JUDGE` / `LLM_WAYPOINT`（定义在 `logistics-service` 的 `application.yml` 根级 `routing:` 下）

A_STAR（默认，最快）：
  GraphHopper路网 + A*搜索算法
  f(n) = g(n) + h(n)
  g=已走代价（实际路网距离），h=启发（Haversine球面距离估计）
  Weighted A*（epsilon参数）：epsilon>1 牺牲最优性换速度

LLM_JUDGE（智能评判）：
  生成3条不同epsilon的A*候选路线
  构建历史上下文（按坐标网格聚合的平均速度/延误统计）
  调DeepSeek：综合候选路线和历史数据，选出最优路线
  
LLM_WAYPOINT（AI路点辅助）：
  调DeepSeek：分析历史拥堵，建议2-3个绕行路点
  抗幻觉：检查LLM返回坐标是否在上海范围内，否则映射到路网最近节点
  分段A*：起点→路点1→路点2→终点，各段单独规划，合并GeoJSON
```

### 10.2 原子库存扣减（防超卖）

```sql
-- 单条 SQL 完成"检查库存够不够"+"扣减"两个操作
-- 数据库行锁保证原子性，不存在并发超卖问题
UPDATE warehouse_product
SET stock = stock - #{quantity}
WHERE product_id = #{productId}
  AND warehouse_id = #{warehouseId}
  AND stock >= #{quantity}  -- 只有库存够才执行

-- Java层检查返回的影响行数：
int affected = mapper.deductStock(...);
if (affected == 0) {
    throw new BusinessException("库存不足");
}
```

### 10.3 响应式网关（WebFlux）

- 传统 Servlet 模型：每个请求占用一个线程（1000并发=1000线程）
- WebFlux 响应式：少量线程处理大量并发（基于 Netty 事件循环）
- 代价：编程模型从 `return result` 变为 `return Mono<ServerResponse>`

```java
// 网关拦截器：响应式写法
return chain.filter(request.mutate().headers(...).build())  // 返回 Mono<Void>
    .then(Mono.empty());                                      // 非阻塞链式调用
```

### 10.4 最终一致性设计

订单发货时，创建配送记录和规划路线是**跨服务调用**，可能因网络/服务故障失败。

系统采用**最终一致性**而非强一致性：

```java
// order-service 发货逻辑
try {
    driverFeignClient.createDelivery(...)   // 可能失败
} catch (Exception e) {
    log.error("创建配送记录失败，待人工补偿: {}", e.getMessage());
    // 不抛异常，不回滚订单
}

try {
    logisticsFeignClient.createRoute(...)  // 可能失败
} catch (Exception e) {
    log.error("创建物流路线失败，待人工补偿: {}", e.getMessage());
    // 不抛异常
}

// 订单状态已更新到"待揽件"
// 即使配送记录/路线创建失败，运维人员可以手动补偿
```

**权衡**：牺牲强一致性，换取服务高可用（单个服务故障不导致整个下单链路崩溃）。

### 10.5 JWT 无状态认证

```
传统 Session 认证（有状态）：
  服务器内存存储 session_id → 用户信息
  水平扩展时需要 Session 共享（Redis）

JWT 认证（无状态）：
  token = header.payload.signature（数字签名）
  payload 中包含用户信息，服务器无需存储
  任意服务节点都能独立验证 token（只需知道密钥）
  
本系统：网关验证 JWT，将用户信息注入请求头（**小写头名**）：
  userId: 1
  username: admin
  roleCode: admin
  
下游服务通过 `@RequestHeader("userId")` 等读取，无需再查数据库
```

## 12. 常见问题与注意事项

### Q1：logistics-service 首次启动非常慢，是正常的吗？

**A**：是正常的。GraphHopper 需要解析 `shanghai.osm.pbf`（上海路网数据文件，约 100MB），建立路网图（`graph-cache/edges`、`graph-cache/nodes`）和空间索引（`graph-cache/location_index`）。首次约需 1-5 分钟。**之后启动会使用缓存**（毫秒级），不需要重新处理。

### Q2：所有服务都需要连接 Nacos 吗？

**A**：是的。所有微服务在启动时向 Nacos 注册自己（`spring.cloud.nacos.discovery.server-addr=127.0.0.1:8848`）。网关通过 Nacos 获取各服务的实际地址，实现 `lb://service-name` 负载均衡。如果 Nacos 未启动，所有服务启动时会报错。

### Q3：前端的 `/api` 代理是怎么工作的？

**A**：Vite 开发服务器（端口 5173）配置了代理规则：所有以 `/api` 开头的请求转发到 `http://localhost:8083`（网关）。这解决了浏览器的**同源策略限制**（不允许 5173 端口的页面直接请求 8083 端口）。生产环境部署时，由 Nginx 配置反向代理替代此功能。

### Q4：JWT Token 中存了哪些信息？

**A**：
```json
{
  "sub": "1",              // userId（主题）
  "username": "admin",     // 用户名
  "roleCode": "admin",     // 角色代码（网关权限判断用）
  "iat": 1700000000,       // 签发时间（issued at）
  "exp": 1700007200        // 过期时间（expired，iat + 7200秒）
}
```

Token 本身不加密（Base64 编码），但有**数字签名**（HMAC-SHA256），篡改后签名验证失败。**不要在 Token 中存密码等敏感信息**。

### Q5：为什么 shop-service 的库存要用数据库 SQL 原子操作，而不是 Java 代码判断？

**A**：Java 代码判断存在并发问题：

```
时间线：
  线程A：查询库存=1  ← 两个线程同时查到1
  线程B：查询库存=1
  线程A：判断1>=1，扣减，库存→0
  线程B：判断1>=1，也扣减，库存→-1  ← 超卖！
```

数据库 `UPDATE ... WHERE stock >= quantity` 是**原子操作**（行锁保护），两个事务不能同时修改同一行：

```
数据库层面：
  线程A：UPDATE ... WHERE stock=1 AND stock>=1 → 成功，stock=0
  线程B：UPDATE ... WHERE stock=0 AND stock>=1 → 影响行数=0，失败
  线程B：Java检测到affected=0 → 抛出"库存不足"异常
```

### Q6：common 模块是怎么被其他服务使用的？

**A**：`common` 不是一个独立运行的服务，而是一个 **Maven 依赖库**（packaging=jar）。其他服务在 `pom.xml` 中声明依赖：

```xml
<dependency>
```

### Q7：为什么 GeoJSON 坐标是 `[经度, 纬度]` 而 Leaflet 要 `[纬度, 经度]`？

**A**：这是历史遗留的不一致问题：
- **GeoJSON（RFC 7946 标准）**：坐标格式是 `[longitude, latitude]`（数学惯例：x=经度，y=纬度）
- **Leaflet（地图库）**：约定使用 `[latitude, longitude]`（地理学惯例：纬度在前）

两者相反！前端 `RouteMap.vue` 中必须做转换：
```typescript
// GeoJSON 坐标：[经度, 纬度]
const coord = [121.55, 31.23]  // [lng, lat]

// Leaflet 需要：[纬度, 经度]
const latlng = [coord[1], coord[0]]  // [lat, lng] = [31.23, 121.55]
```
