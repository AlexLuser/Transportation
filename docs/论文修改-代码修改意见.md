# 论文修改对应的项目代码修改意见

本文依据 `docs/论文修改.md` 的要求，对当前项目代码做了定向阅读，重点关注 ToB 物流平台定位、角色边界、司机末端派送链路、中转站作业与论文表述的一致性。当前建议以“先服务论文修改”为优先级，分为立即建议、论文写法建议和后续代码修复建议。

## 一、总体定位建议

当前系统代码里同时存在“顾客/商城/商品浏览/个人寄件”和“商户发货/仓储/调度/干线/末端配送”两套语义。论文应明确收敛为：

> 面向商家的 ToB 智能物流协同平台，商家作为发货主体，消费者仅作为收件信息与物流查询对象，不作为平台交易主体。

因此论文中不建议再把系统描述成电商平台，也不建议强调“顾客购买商品”。应改为“商家录入承运物、备货出库、提交运输需求，平台完成调度、干线运输、中转处理和末端派送”。

## 二、前端与角色边界修改意见

### 1. Sender/Customer 角色

相关文件：

- `frontend/src/router/index.ts`
- `frontend/src/pages/CustomerHome.vue`
- `frontend/src/pages/Customer/Product.vue`
- `frontend/src/pages/Customer/CatalogShipment.vue`
- `frontend/src/pages/Customer/ShopPage.vue`

当前 `customer` 角色被路由到 `/sender/home`，但默认重定向到 `/sender/home/products`，侧边栏也显示“货物目录”。这会让论文和系统截图呈现出“面向消费者浏览商品”的电商形态。

建议：

1. 将 `/sender/home` 默认页改为 `/sender/home/shipment`，使登录后直接进入“发起寄件”或“运单创建”页面。
2. 从 `CustomerHome.vue` 菜单中移除“货物目录”入口。
3. 保留 `orders` 和 `profile`，用于查看自己的运单和基础信息。
4. `Product.vue`、`CatalogShipment.vue`、`ShopPage.vue` 暂时可以不删，但应从路由和菜单隐藏，避免论文截图出现商城/商品橱窗。
5. 如果论文仍需要解释 customer 角色，建议称为“收件/寄件测试用户”或“消费者运单查询用户”，不要称为核心业务主体。

论文表述建议：

> 本系统的核心业务主体为商户、运输员和平台管理员。消费者信息主要作为运单收件信息存在，系统不承担交易撮合与商品销售功能。

### 2. Merchant/Shop 角色

相关文件：

- `frontend/src/pages/ShopHome.vue`
- `frontend/src/pages/Shop/Product.vue`
- `frontend/src/pages/Shop/Stock.vue`
- `frontend/src/pages/Shop/Warehouse.vue`
- `shop-service/src/main/java/com/fm/shop/service/*`

当前商户端的商品、库存、仓库能力可以保留，但论文中应重新命名业务语义：

- “商品管理”建议改为“承运物管理”或“货品档案管理”。
- “商品库存”建议改为“仓储库存”。
- “商城展示”相关能力不作为主流程展示。

这比删除商户商品/库存模块更合适，因为商户发货需要有货品档案和库存基础，只是它们不应被解释为对外销售商品。

### 3. Admin 角色

相关文件：

- `frontend/src/pages/AdminHome.vue`
- `frontend/src/pages/Admin/Goods.vue`
- `frontend/src/api/mall.ts`
- `gateway-service/src/main/java/com/fm/gateway/filter/JwtAuthFilter.java`

当前管理员侧有“商品管理”菜单，并且 `Goods.vue` 会查看所有商品、价格、销量、上架状态。这与物流系统定位冲突。

建议优先级：

1. 论文中不要展示管理员“商品管理”页面截图。
2. 若要小改前端，将菜单“商品管理”改为“承运物审核”或直接隐藏该菜单。
3. `Goods.vue` 中“售价、原价、销量、上架”等字段应避免出现在论文系统设计里；若保留页面，应改为“承运物名称、编码、所属商户、重量、单位、状态、审核”。
4. 网关中 `/api/products` 目前允许 `shop` 和 `customer` 访问，`/api/mall` 允许 `shop/customer/admin` 访问。若后续真正收敛为 ToB，应将 `/api/mall` 从客户侧业务入口移除，或只作为内部测试接口。

## 三、登录与注册问题修改意见

相关文件：

- `auth-service/src/main/java/com/fm/auth/service/impl/AuthServiceImpl.java`
- `frontend/src/pages/Register.vue`
- `frontend/src/router/index.ts`
- `user-service/src/main/java/com/fm/user/*`

你提到“目前只能登录 admin”。从代码看，登录逻辑本身支持 `customer/shop/driver/admin`，但商户和司机注册后默认进入待审核状态：

- shop 注册后 `ShopRegistration.status = 2`
- driver 注册后 `DriverRegistration.status = 2`
- 登录时如果状态为 2，会返回“账号待审核”

因此“只能登录 admin”的常见原因不是路由只支持 admin，而是测试账号没有通过管理员审核，或者数据库里没有可登录的非 admin 账号。

建议：

1. 论文中可以写“商户与司机账号需经管理员审核后启用”，这与现有代码一致。
2. 测试数据中应准备至少 1 个已审核商户账号、1 个已审核司机账号。
3. 管理端用户审核页需要保证能把 `status=2` 改为通过状态。若测试时没有该流程，可以直接在数据库种子数据中设置为通过。
4. 注册页目前仍显示“顾客”，建议改为“发货测试用户”或从注册入口中移除 customer，避免 ToB 定位冲突。

## 四、中转站角色的论文处理建议

相关文件：

- `frontend/src/pages/Admin/HubOperations.vue`
- `frontend/src/pages/Admin/Hubs.vue`
- `logistics-service/src/main/java/com/fm/logistics/entity/HubSortingRecord.java`
- `logistics-service/src/main/java/com/fm/logistics/entity/HubOutboundRecord.java`
- `logistics-service/src/main/java/com/fm/logistics/service/impl/LogisticsBatchServiceImpl.java`

当前系统已有中转站管理、中转站作业记录、干线到达后激活末端路线等能力，但没有独立 `hub_operator` 角色。你的论文可以这样处理：

> 当前版本中，中转站作业由管理员统一调度与维护；系统在数据库实体与接口层已预留中转站入库、出库、分拣及批次交接记录，后续可扩展独立中转站操作员角色，实现基于扫描的进仓、出仓和分拣确认。

论文系统设计章节可以画出独立“中转站操作员”参与者，但实现章节应说明本版本由管理员菜单“中转站作业”承载，避免答辩时被问到为什么没有单独登录角色。

## 五、司机末端派送无数据的排查结论

相关文件：

- `frontend/src/pages/Driver/Delivery.vue`
- `frontend/src/api/driver.ts`
- `driver-service/src/main/java/com/fm/driver/controller/DeliveryController.java`
- `driver-service/src/main/java/com/fm/driver/service/impl/DeliveryServiceImpl.java`
- `driver-service/src/main/java/com/fm/driver/mq/DeliveryConsumer.java`
- `logistics-service/src/main/java/com/fm/logistics/service/impl/LogisticsBatchServiceImpl.java`
- `logistics-service/src/main/java/com/fm/logistics/mq/RouteConsumer.java`

司机端“待接单大厅”读取的是：

```text
GET /api/drivers/deliveries/pending
```

后端实际查询的是 `order_delivery.delivery_status = 0` 的配送记录。因此司机端无数据，核心排查方向是：末端路线是否已经被转换成 `order_delivery` 记录。

当前链路如下：

1. 管理员创建配送批次。
2. 如果使用 Hub 模式，系统先创建干线配送记录。
3. 干线司机接单并开始运输。
4. 干线司机点击“到达中转站”。
5. driver-service 发送 `HubArrivalMessage`。
6. logistics-service 消费消息，调用 `activateLastMileRoutes(batchId)`。
7. logistics-service 对末端路线发送 `LastMileActivateMessage`。
8. driver-service 消费消息，调用 `createLastMileDelivery`，写入 `order_delivery`。
9. 司机端待接单大厅才能看到末端配送任务。

所以如果末端派送无数据，优先检查：

1. 干线任务是否已经执行“到达中转站”，只创建批次不会让 Hub 模式的末端任务立即出现。
2. RabbitMQ 中 `hub.arrival` 和 `last.mile.activate` 两个消息是否正常消费。
3. `last.mile.activate.queue` 是否有堆积或进入死信队列。
4. `logistics_route` 中末端路线是否仍为 `route_status = -1`；如果是，说明还没激活。
5. `order_delivery` 中是否已生成 `segment_type = 2` 且 `delivery_status = 0` 的记录。
6. 多停靠末端路线 `order_id = null` 是正常设计，不应据此判断数据异常；页面已经通过 `routeId` 加载停靠点。

一个潜在问题：

`RouteConsumer.handleRouteStatusUpdate` 当前按 `orderId` 更新路线状态。干线和多停靠末端的 `orderId` 可能为 null，因此普通“状态更新”消息不适合这些路线。代码里已对部分场景做了 Controller 层补偿，但后续建议把 `RouteStatusMessage` 扩展为支持 `routeId`，避免空 `orderId` 导致路线状态不同步。

## 六、末端派送：管理员排单还是司机接单

结合 ToB 物流平台，建议论文采用“管理员统一调度为主，司机接单为辅”的表述。

理由：

1. ToB 物流强调时效、路线成本、批次合并和责任可追踪，不适合完全依赖司机自由抢单。
2. 当前系统已有管理员侧“城市末端调度”“配送批次”“全国干线”等页面，更适合解释为管理员先生成调度方案。
3. 当前司机端存在“待接单大厅”，可以解释为轻量实现：系统生成调度任务后，司机从待分配任务中确认承接。
4. 如果答辩强调合理性，可以说后续会扩展“管理员指派司机”，现阶段使用司机确认接单降低排班模块复杂度。

论文推荐写法：

> 平台采用“系统智能调度 + 人工确认”的模式。管理员基于调度池、路线规划和批次结果生成运输任务，司机端负责确认承接、状态上报和到达确认。该设计既保证平台对运输过程的统一调度，又保留一线司机对车辆和执行状态的确认能力。

## 七、术语替换建议

建议在论文和页面截图中统一替换以下术语：

| 当前术语 | 建议术语 | 原因 |
| --- | --- | --- |
| 商品 | 承运物 / 货品 | 避免电商交易语义 |
| 商品管理 | 承运物管理 / 货品档案 | 强调物流承运对象 |
| 商城 | 货品目录 / 不展示 | ToB 物流不做消费购买 |
| 顾客 | 收件人 / 消费者信息 | 消费者不是平台主要用户 |
| 买家订单 | 运单 / 发货单 | 物流系统核心对象是运单 |
| 揽收队列 | 待揽收 | 表示货物已打包待取 |
| 司机 | 运输员 / 配送员 | 与系统内“driver”角色对应 |

## 八、论文优先的截图与章节建议

建议论文重点展示这些页面和模块：

1. 登录注册与角色审核：体现权限控制。
2. 商户仓储/承运物维护：体现发货主体是商家。
3. 管理员城市末端调度：体现平台调度能力。
4. 全国干线与 MCMF 规划：体现算法特色。
5. 中转站作业：说明当前由管理员统一操作，预留独立角色。
6. 司机配送任务与状态上报：体现运输执行闭环。
7. 物流轨迹查询：体现运单跟踪。

不建议论文重点展示：

1. 顾客浏览商品。
2. 商城页面。
3. 商品售价、销量、上架促销。
4. 对外商品橱窗。

## 九、后续代码修改优先级

### P0：论文截图前建议完成

1. `frontend/src/router/index.ts`：将 customer 首页重定向从 `products` 改为 `shipment`。
2. `frontend/src/pages/CustomerHome.vue`：隐藏“货物目录”菜单。
3. `frontend/src/pages/AdminHome.vue`：隐藏或重命名“商品管理”。
4. `frontend/src/pages/Register.vue`：将“顾客”文案改为“发货测试用户”或暂时移除 customer 注册选项。
5. 准备已审核的 shop、driver 测试账号。

### P1：答辩演示前建议完成

1. 给 `RouteStatusMessage` 增加 `routeId`，让干线和多停靠路线状态更新不依赖 `orderId`。
2. 在司机端待接单大厅增加任务来源字段：干线、末端、直送、多停靠。
3. 在管理员调度页面把“揽收队列”统一改成“待揽收”。
4. 管理员侧商品页改名为“承运物审核”，移除价格、销量等电商字段。
5. 在中转站作业页展示入库、出库、分拣三类状态，哪怕当前由管理员操作。

### P2：毕业后或扩展版本

1. 新增 `hub_operator` 角色与独立登录入口。
2. 增加管理员指派司机能力，而不是只靠司机接单。
3. 移除或隔离 `/api/mall`，把商户货品目录改为内部仓储资料。
4. 为 MQ 关键链路增加失败重试监控和死信队列可视化。
5. 为批次、路线、配送单增加统一状态机，减少订单状态、路线状态、配送状态之间的不一致。

## 十、结论

当前代码已经具备支撑论文中“智能物流平台”的主要骨架：多角色认证、商户仓储、调度池、批次、Hub-and-Spoke、MCMF 全国干线、司机执行和物流追踪。主要问题不是功能完全缺失，而是业务命名和角色边界仍残留电商系统语义。

论文修改时应优先做概念收敛：把系统解释为“商户发货物流平台”，把商品解释为“承运物/货品档案”，把客户侧购物功能降级为测试入口或非核心模块。代码层面最小改动是隐藏商城与商品橱窗入口、修正菜单术语、准备通过审核的测试账号，并按上文链路排查末端派送数据是否成功进入 `order_delivery`。
