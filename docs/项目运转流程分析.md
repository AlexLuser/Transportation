### 2.2 两种下单路径

#### 路径 A：商户订单 (orderType=0)

顾客在商城选购 → 下单 → 商户备货 → 商户发货 → 物流调度

```
顾客下单 → order-service.createOrder()
         → 验证地址(Feign: customer-service)
         → 验证商品+库存预检(Feign: shop-service)
         → 订单落库，status=1(待发货)，paymentStatus=1(已支付)
         → MQ: stock.deduct → shop-service 异步扣减库存
         → 返回订单详情

商户发货 → order-service.shipOrder()
         → 获取收货地址坐标(Feign: customer-service)
         → Hub分配(Feign: logistics-service.assignHubs) ← 判断同城/跨城
         → 更新订单 status=2(待揽件) + originHubId/destHubId
         → MQ: dispatch.pool.add → logistics-service 入调度池
         → 自动创建出库单(Feign: shop-service) ← 扣减库存
```

#### 路径 B：个人寄件 (orderType=1)

顾客直接发快递 → 支付后自动入调度池 → 跳过商户发货步骤

```
顾客寄件 → order-service.createPersonalShipment()
         → 验证取件/收件地址(Feign: customer-service)
         → 运费计算：基础12元 + 超出1kg部分每kg加2元
         → 订单落库，status=0(待支付)，paymentStatus=0

顾客支付 → order-service.payOrder()
         → Hub分配(Feign: logistics-service.assignHubs)
         → 更新订单 status=2(待揽件) + paymentStatus=1
         → MQ: dispatch.pool.add → logistics-service 入调度池
           (dispatchOriginType=2，使用发件人坐标作为调度起点)
```

## 三、智能调度系统（核心！多订单处理的关键）

当大量订单进入系统后，**调度池 + VRP + MCMF + Hub-Spoke** 构成了处理海量订单的核心引擎。

### 3.1 调度池 (dispatch_pool)

所有待配送订单统一进入调度池，由管理员（或定时任务）触发批次创建：

```
dispatch_pool 表字段：
  - order_id, shop_id, warehouse_id
  - end_address, end_lat, end_lng    ← 收货地址
  - dispatch_origin_lat/lng/addr     ← 调度起点坐标（仓库或发件人地址）
  - origin_hub_id, dest_hub_id       ← Hub 分配结果
  - is_cross_city                    ← 是否跨城
  - dispatch_origin_type             ← 0=仓库 2=个人寄件
  - status                           ← 0=待调度 1=已调度
  - enter_time                       ← 入池时间
```

### 3.2 批次创建流程 (createBatch) — 同城配送

管理员从调度池选出一批同仓/同区域的订单，触发 `createBatch()`：

```
  ┌─────────────────────────────────────────────────────────────┐
  │                    createBatch() 核心流程                      │
  │                                                              │
  │  1. VRP 规划最优访问顺序                                      │
  │     ├─ 最近邻贪心 (N≤15)                                      │
  │     └─ 2-opt 局部优化 (N>15)                                  │
  │                                                              │
  │  2. 智能选 Hub（可选）                                        │
  │     ├─ 前端指定 Hub → 直接使用                                │
  │     └─ LLM 智能选择 → 综合距离+负载+交通多因素                 │
  │                                                              │
  │  3. 创建批次记录 (logistics_batch)                            │
  │                                                              │
  │  4. 创建干线的路线（仓库 → Hub）                              │
  │     segment_type=1，MQ 通知 driver-service 创建干线配送单       │
  │                                                              │
  │  5. 末端 K-Means 分组 + 多停靠路线创建                        │
  │     ├─ K-Means 按地理位置聚类（每司机最多4停靠点）              │
  │     ├─ 组内按 VRP 全局顺序排列                                │
  │     └─ 每组创建一条末端路线 → MQ 通知 driver-service            │
  │                                                              │
  │  6. 汇总返回 BatchDetailDTO                                  │
  └─────────────────────────────────────────────────────────────┘
```

#### VRP（车辆路径规划）算法

| 订单数 | 算法 | 说明 |
|--------|------|------|
| N ≤ 15 | 最近邻贪心 | O(N²)，从仓库出发依次选最近的未访问点 |
| N > 15 | 2-opt 局部优化 | 在贪心基础上反复交换边，直到无改进 |

#### K-Means 末端分组

- 聚类维度：经纬度（Haversine 球面距离）
- 分组数 k = ⌈N / 4⌉（每司机最多4个停靠点）
- 迭代上限 50 轮
- 组内停靠顺序遵循 VRP 全局最优顺序

### 3.3 跨城配送 — Hub-Spoke + MCMF

当订单跨城时（originHub ≠ destHub），系统使用 **MCMF（最小费用最大流）** 算法进行跨城干线调度：

```
  ┌──────────┐    MCMF 规划     ┌──────────┐    末端配送    ┌──────────┐
  │ 发货城市  │ ──────────────▶  │ 全国Hub   │ ──────────▶   │ 收货城市  │
  │ 本地Hub  │    干线运输       │ 中转网络   │    末端配送   │ 本地Hub  │
  └──────────┘                  └──────────┘              └──────────┘
```

#### MCMF 算法细节

系统实现了两种 MCMF 算法：

1. **单商品 MCMF**：SSP（逐次最短路）+ SPFA
   - 每个 Hub 拆成入港/出港两个节点
   - 超级源 → 各发货 Hub（供给量）→ 运输边（容量+单位费用）→ 各收货 Hub → 超级汇（需求量）
   - 每次 SPFA 找最短费用路，沿路增广

2. **多商品 MCMF**：Dijkstra-SSP，每 OD 对独立寻路，共享边容量
   - 按需求量降序处理 OD 对（高需求优先占容量）
   - 每对独立执行 Dijkstra 找最低费用路径
   - 沿路径增广 min(瓶颈容量, 剩余需求)
   - 解决了「同一 Hub 供给与需求代数抵消」的建模缺陷

#### 跨城流程

```
1. MCMF 规划 → 确定各 Hub 间的流量分配
   ├─ 输入：全国 Hub 网络拓扑 + 各 Hub 供给/需求 + 链路容量+成本
   └─ 输出：每条干线边实际流量 + 最小总成本

2. FlowPlan 创建 → 按日期组织跨城流量规划
   ├─ 将 MCMF 结果持久化为 flow_plan + flow_plan_item
   └─ 每个 flow_plan_item 记录：fromHub → toHub, 订单数, 干线批次

3. 干线运输 → 驱动员在待接单大厅接干线配送单
   ├─ 从发货 Hub → 目标 Hub（经停或直达）
   └─ 到达 Hub 后 MQ: hub.arrival → logistics-service 激活末端路线

4. 末端配送 → 与同城末端相同（VRP + K-Means 分组）
```

### 5.2 关键并发处理机制

| 机制 | 说明 |
|------|------|
| **MQ 异步** | 库存扣减、调度池入池、配送单创建均异步解耦，下单接口不阻塞 |
| **调度池** | 订单先入池排队，由管理员/定时任务批量调度，避免单订单单司机低效 |
| **VRP 批量优化** | N个订单合并为1个批次，1个司机跑N个点，而非N个司机各跑1个点 |
| **K-Means 分组** | 自动将N个订单分成⌈N/4⌉组，每组1个司机最多4个停靠点 |
| **Hub-Spoke** | 同城走Hub中转降配送半径；跨城走MCMF做干线流量优化 |
| **MCMF** | 跨城时全局最优分配干线运力，最小化总运输成本 |
| **LLM 智能决策** | Hub选择、路径策略（A*/多停靠/LLM推荐）均由 DeepSeek 辅助决策 |
| **死信队列** | MQ 消费失败3次后自动进入DLQ，保障消息不丢失，可人工介入 |
| **Redis 缓存** | 驱动信息、Hub坐标等高频查询走缓存，降低DB压力 |

### 5.3 实际场景举例

**场景：双十一期间上海某仓库同时产生 1000 个同城订单 + 200 个跨城订单**

1. **入池阶段**（秒级）
   - 1000 个订单通过 MQ 异步入调度池（`dispatch.pool.add`）
   - 200 个跨城订单同步入池，但标记 `is_cross_city=1`

2. **同城调度**（管理员触发或定时）
   - 将 1000 个订单按仓库分组
   - 每组调用 `createBatch()`：
     - VRP 排出最优访问顺序
     - K-Means 分成 250 组（1000/4=250）
     - 创建 250 条末端路线 → 250 名司机各跑 4 个点
   - 不走 Hub 时：直接从仓库出发多停靠配送

3. **跨城调度**（MCMF 规划）
   - 管理员在 MCMF 面板触发日度规划
   - 输入：200 个 OD 需求 + Hub 网络拓扑
   - MCMF 算法输出：各干线段流量分配
   - 创建 FlowPlan → 干线批次 → 司机接干线单

4. **配送执行**
   - 司机在待接单大厅看到可用路线（干线/末端）
   - 接单 → 绑定路线（MQ #10）→ 更新订单状态为派送中（MQ #9）
   - 配送完成 → 更新订单状态为待签收/已完成（MQ #9）
   - 跨城干线到达 Hub → 激活末端路线（MQ #13）→ 末端司机接单

5. **异常处理**
   - 司机取消 → 订单回退待揽件（MQ #12）→ 重新入调度池
   - MQ 消费失败 → 重试3次 → 死信队列 → 人工介入

## 七、经验教训

1. **MQ 异步是关键**：库存扣减、调度池入池都是异步的，下单接口本身只做同步验证+落库
2. **批量优于单件**：VRP 让一个司机跑4个点比4个司机各跑1个点效率高得多
3. **Hub-Spoke 降半径**：同城走Hub中转虽然多一段干线，但末端配送半径大幅缩短
4. **MCMF 全局最优**：跨城运力有限时，MCMF 保证总成本最低的流量分配
5. **LLM 不是万能的**：LLM 用于辅助决策（选Hub、选策略），核心算法（VRP/MCMF）仍用确定性的图算法
6. **死信队列保底**：所有 MQ 消费都有3次重试 + DLQ，消息不会丢失
